About me

Where I’m coming from, why I chose AI engineering, and what I work with.

I’m an AI engineering student. Most of what I know so far comes from labs, group projects and things I built because I wanted to see them work.

I chose AI engineering because I like the point where a model meets the real world. Handwriting, speech and photos are messy, and getting a model to cope with them means making choices about data, cost and speed that a textbook skips over. I would rather learn by building: a voice assistant I can talk to, a classifier that recognizes Baybayin characters, a 3D scene generated from a script.

Right now I’m practicing Python for machine learning and C++ for data structures, and I write up what I learn in the reflections below.

Personal project

Voice assistant

A Jarvis-style assistant I can talk to. It records a short clip, turns it into text, sends the conversation so far to Claude, and reads the reply aloud. I kept it small on purpose so the API cost stays low for everyday use.

  1. RecordA five-second clip from the microphone
  2. TranscribeWhisper turns the speech into text
  3. ReplyClaude answers, using the conversation so far
  4. Speakpyttsx3 reads the answer aloud

Then the loop starts again.

Planned next

  • Silence detection instead of a fixed five seconds
  • A wake word with Porcupine
  • A more natural voice with ElevenLabs

Tools Python, Whisper, Anthropic API, pyttsx3

Reflections

A small blog of short entries about what I have learned, built or got stuck on.

Small and cheap on purpose

From my voice assistant

My voice assistant listens for exactly five seconds and then stops. That is a crude rule: it can cut me off mid-sentence, and it wastes time when I say nothing. I started there because it was the simplest thing that could work, and it let me test the whole chain from microphone to spoken reply before polishing any one part.

It also taught me that every turn costs money, because the model receives the whole conversation again each time. So the plan is to get smarter about when to stop listening, and to keep an eye on how much text I send. A project I cannot afford to run every day is not one I will keep improving.

Same kind of network, different data

From my neural network labs

MNIST was my starting point: small images, ten classes and a clear right answer. The fruit and Baybayin labs used convolutional networks on new kinds of images, including handwriting that changes from one writer to the next.

What stood out is that the network code looked similar across all three, while the questions about the data kept changing. Are the classes balanced? Are the labels right? Would a new person’s handwriting look like the examples? Most of the work in machine learning, I’m learning, is understanding the data well enough to know what you are really asking the model to do.

Six models, one question

From the retail forecasting lab

In the forecasting lab I trained Linear Regression, Ridge, Lasso, Random Forest, XGBoost and LightGBM on the same Walmart data. Seeing six results next to each other taught me more than any single model could.

A model’s name tells you little until you measure it, and a simple baseline shows whether the complicated models are earning their extra complexity. I want to keep that habit: start plain, test every model the same way, and report the numbers instead of the buzzwords.

Building a stack from nothing

From my AIE105 group project

For our group project we are writing a C++ calculator that follows PEMDAS, and the stacks are linked lists we build ourselves, with no vectors allowed. On a slide a stack looks trivial. In code, every push and pop is a decision about pointers, and the calculator only works if all of those small decisions are right.

We also have to draw a flowchart of the main program, which pushes us to agree on the logic as a group before we argue about syntax. I am finding that explaining a design clearly is half of building it.
